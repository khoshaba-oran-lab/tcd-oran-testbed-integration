# Native gNB Telemetry

## 1. Purpose and scope

This document defines the native gNB telemetry path used by the Sci_O-RAN Tb3 experimental platform.

The purpose of this document is to establish an evidence-based description of:

- the source of the native scheduler metrics;
- the gNB-to-host telemetry transport;
- the configured and observed reporting periods;
- the JSON record structure;
- timestamp semantics;
- UE-level and cell-level metric semantics;
- the distinction between interval aggregates and persistent state variables;
- the native-metrics schema required for future unified Sci_O-RAN datasets.

This document covers the native JSON scheduler telemetry generated by the srsRAN gNB.

The E2SM-KPM telemetry path is a separate observability mechanism and must not be interpreted as the source of the native metrics described here.

## 3. Native metrics configuration

The BASE-05 gNB configuration contains:

```yaml
metrics:
  addr: 10.53.1.1
  port: 55555
  enable_json_metrics: true
  sched_report_period: 1000
```

The exact srsRAN source converts `sched_report_period` to:

```cpp
std::chrono::milliseconds{config.metrics.sched_report_period}
```

Therefore:

```text
configured scheduler metrics report period = 1000 ms
```

This value is the configured scheduler reporting period. It must not be interpreted as a guarantee that UDP telemetry records will be observed at an exact wall-clock interval of 1.000 s.

## 4. Native telemetry transport

### 4.1 gNB JSON metrics pipeline

The exact srsRAN source creates the JSON metrics sink using:

```cpp
srslog::fetch_udp_sink(
    gnb_cfg.metrics_cfg.addr,
    gnb_cfg.metrics_cfg.port,
    srslog::create_json_formatter());
```

When native JSON scheduler metrics are enabled, the DU scheduler metrics pipeline connects:

```text
scheduler metrics report
        |
        v
scheduler_cell_metrics_consumer_json
        |
        v
srslog JSON channel
        |
        v
JSON formatter
        |
        v
UDP sink
```

For the investigated Tb3 BASE-05 deployment, the runtime transport path is:

```text
gNB container
10.53.1.3
        |
        | UDP JSON telemetry
        v
10.53.1.1:55555
host / Docker bridge gateway
        |
        v
Sci_O-RAN native metrics receiver
```

The destination address and port are therefore:

```text
destination address = 10.53.1.1
destination port    = 55555/udp
```

Runtime inspection confirmed the gNB container address:

```text
10.53.1.3
```

During the investigated run, the receiver observed:

```text
SRC=10.53.1.3:52084
```

The UDP source port `52084` is a runtime-observed ephemeral source port. It is not part of the fixed native telemetry configuration and must not be encoded as a constant in the dataset schema.

### 4.2 Raw receiver

The raw Sci_O-RAN receiver is implemented by:

```text
scripts/tb3-native-metrics-receiver.sh
```

For each UDP datagram the receiver records:

- `WALL_NS` using `time.time_ns()`;
- `MONO_NS` using `time.monotonic_ns()`;
- source IPv4 address and UDP port;
- datagram size in bytes;
- the complete decoded JSON payload.

An observed receiver record begins with:

```text
WALL_NS=1786214151397002429
MONO_NS=121904618880662
SRC=10.53.1.3:52084
BYTES=668
DATA={...}
```

The wall-clock and monotonic receive timestamps serve different purposes and must not be collapsed into one field.

`WALL_NS` provides a host-side epoch-based receive timestamp suitable for correlation with other epoch-based observability sources.

`MONO_NS` provides a monotonic receive clock suitable for inter-arrival calculations because it is not affected by host wall-clock corrections.

### 4.3 Compact parser

The compact parser is implemented by:

```text
scripts/tb3-native-metrics-compact.sh
```

It extracts selected cell-level and UE-level fields from the same native JSON stream.

The current parser computes its displayed `dt_ms` from receiver-side wall-clock time. For reproducible unified-dataset processing, monotonic receive time should instead be retained and preferred for receiver-side interval calculations.

The compact field:

```text
cell_avg_latency
```

is an alias of native JSON:

```text
cell_metrics.average_latency
```

It must always retain the scheduler-decision-latency semantics defined later in this document. It must never be interpreted as network RTT.


## 5. Native JSON timestamp semantics

The native scheduler JSON record contains a root-level field named `timestamp`.

The exact srsRAN implementation is:

```cpp
/// Returns the current time in seconds with ms precision since UNIX epoch.
static double get_time_stamp()
{
  auto tp = std::chrono::system_clock::now().time_since_epoch();
  return std::chrono::duration_cast<std::chrono::milliseconds>(tp).count() * 1e-3;
}
```

The JSON consumer writes this value immediately before sending the metrics context to the JSON log channel:

```cpp
ctx.write<metric_timestamp_tag>(get_time_stamp());
log_chan(ctx);
```

Therefore the native JSON `timestamp` has the following proven semantics:

| Property | Definition |
|---|---|
| Source | gNB JSON metrics consumer |
| Clock | `std::chrono::system_clock` |
| Epoch | UNIX epoch |
| Unit | seconds |
| JSON type | `double` |
| Implementation resolution | 1 ms |
| Meaning | wall-clock time when the gNB JSON metrics record is constructed |

An observed value was:

```json
"timestamp": 1786214151.3960001
```

This timestamp must not be interpreted as:

- a radio-frame timestamp;
- a scheduler slot index;
- a PHY sample counter;
- a monotonic timestamp;
- an RTT measurement.

### 5.1 Time fields required for the unified dataset

Three separate timestamps shall be retained for native telemetry:

| Dataset field | Source | Unit | Purpose |
|---|---|---:|---|
| `gnb_timestamp_s` | JSON `timestamp` | s | gNB-generated UNIX wall clock |
| `rx_wall_ns` | receiver `time.time_ns()` | ns | host receive epoch time |
| `rx_mono_ns` | receiver `time.monotonic_ns()` | ns | robust receive inter-arrival timing |

These fields represent different time domains and shall not overwrite one another.

For receiver-side interval measurements, `rx_mono_ns` is preferred because a monotonic clock is not affected by host wall-clock corrections.

For correlation with other epoch-based observability sources, `gnb_timestamp_s` and `rx_wall_ns` shall be preserved.

## 6. Configured and observed reporting period

The BASE-05 configuration specifies:

```text
sched_report_period = 1000 ms
```

The scheduler implementation converts the configured period into a number of scheduler slots after the slot numerology is known.

The relevant logic is:

```cpp
usecs slot_dur = usecs{1000U >> sl_tx.numerology()};
report_period_slots = usecs{report_period} / slot_dur;
```

A report is generated when:

```cpp
slot_counter >= report_period_slots
```

Therefore the configured value defines the scheduler reporting window, but it does not imply that host-observed JSON datagrams must arrive at an exactly constant 1000 ms wall-clock interval.

### 6.1 Tb3 empirical interval measurement

A 30-second native telemetry capture produced:

```text
28 datagrams
27 inter-arrival intervals
```

The source endpoint during this capture was:

```text
10.53.1.3:52084
```

Statistics calculated from consecutive gNB JSON timestamps were:

| Statistic | `GNB_DT_MS` |
|---|---:|
| Number of intervals | 27 |
| Mean | 1065.741 ms |
| Median | 1064.000 ms |
| Minimum | 1060.000 ms |
| P95 | 1076.700 ms |
| P99 | 1077.740 ms |
| Maximum | 1078.000 ms |
| Standard deviation | 4.621 ms |

Statistics calculated independently from host monotonic receive timestamps were:

| Statistic | `RX_MONO_DT_MS` |
|---|---:|
| Number of intervals | 27 |
| Mean | 1065.742 ms |
| Median | 1064.215 ms |
| Minimum | 1059.832 ms |
| P95 | 1076.746 ms |
| P99 | 1077.608 ms |
| Maximum | 1077.825 ms |
| Standard deviation | 4.651 ms |

The two independent interval measurements are nearly identical:

```text
mean GNB timestamp delta = 1065.741 ms
mean host monotonic delta = 1065.742 ms
```

This demonstrates that the approximately 65 ms difference relative to the configured 1000 ms reporting period is not introduced by the Sci_O-RAN UDP receiver.

For this investigated Tb3 run, the observed effective wall-clock telemetry interval was approximately:

```text
1.066 s
```

This value is an empirical property of the measured run. It must not be treated as a universal constant of srsRAN or of the Tb3 platform.

### 6.2 gNB-to-receiver wall-clock difference

The measured difference:

```text
rx_wall_ns - gNB_timestamp
```

had the following statistics:

| Statistic | Difference |
|---|---:|
| Mean | 0.778 ms |
| Median | 0.779 ms |
| Minimum | 0.290 ms |
| P95 | 1.180 ms |
| P99 | 1.211 ms |
| Maximum | 1.215 ms |
| Standard deviation | 0.269 ms |

This quantity is not RTT.

It is a local one-way timing difference between the timestamp created in the gNB JSON consumer and the timestamp taken by the host receiver after the UDP datagram is delivered. It can include JSON/logging processing, UDP delivery, Docker networking, process scheduling, and timestamp quantization.

### 6.3 Dataset timing rule

Future Sci_O-RAN processing shall not synthesize native telemetry timestamps using an assumed constant:

```text
Ts = 1.000 s
```

The actual timestamps contained in and associated with every received record shall be retained.

The following two quantities must remain explicitly distinct:

```text
configured scheduler report period = 1000 ms
observed effective telemetry interval = measured from actual timestamps
```

This distinction is required for time-series alignment, system identification, latency analysis, and later closed-loop control experiments.


## 7. Cell-level scheduler metrics

The native JSON record contains a cell-level object of the form:

```json
"cell_metrics": {
  "error_indication_count": 0,
  "average_latency": 16,
  "latency_histogram": [1000, 0, 0, 0, 0, 0, 0, 0, 0, 0]
}
```

### 7.1 `average_latency`

In the exact investigated srsRAN source, the scheduler metric is declared as:

```cpp
std::chrono::microseconds average_decision_latency{0};
```

The JSON consumer serializes:

```cpp
metrics.average_decision_latency.count()
```

The ordinary metrics log independently renders the same value as:

```text
mean_latency=<value>usec
```

Therefore the native JSON field:

```text
cell_metrics.average_latency
```

has the proven unit:

```text
microseconds
```

and represents:

```text
internal gNB scheduler decision latency
```

The scheduler accumulates one latency value for every processed scheduler slot:

```cpp
decision_latency_sum += slot_decision_latency;
```

and calculates the report value as:

```cpp
average_decision_latency =
    decision_latency_sum / report_period_slots;
```

Consequently, a JSON value such as:

```json
"average_latency": 16
```

means an average scheduler decision latency of approximately:

```text
16 us
```

for the corresponding scheduler reporting window.

### 7.2 Critical interpretation rule

The compact Sci_O-RAN parser exposes this field using the alias:

```text
cell_avg_latency
```

The following equivalence shall therefore be used:

```text
cell_avg_latency
    =
cell_metrics.average_latency
    =
average internal gNB scheduler decision latency in microseconds
```

`cell_avg_latency` must never be interpreted as:

- IP round-trip time;
- UE-to-gNB RTT;
- application RTT;
- user-plane end-to-end latency;
- radio propagation delay;
- packet delivery latency.

Network RTT and user-plane latency must be measured by separate observability sources.

### 7.3 Scheduler latency histogram

The scheduler defines:

```cpp
static constexpr unsigned latency_hist_bins = 10;
static constexpr unsigned nof_usec_per_bin  = 50;
```

For every scheduler slot, the histogram index is calculated as:

```cpp
unsigned bin_idx =
    slot_decision_latency.count() /
    scheduler_cell_metrics::nof_usec_per_bin;

bin_idx =
    std::min(
        bin_idx,
        scheduler_cell_metrics::latency_hist_bins - 1);

decision_latency_hist[bin_idx]++;
```

The resulting histogram semantics are:

| Bin | Scheduler decision latency |
|---:|---:|
| 0 | 0-49 us |
| 1 | 50-99 us |
| 2 | 100-149 us |
| 3 | 150-199 us |
| 4 | 200-249 us |
| 5 | 250-299 us |
| 6 | 300-349 us |
| 7 | 350-399 us |
| 8 | 400-449 us |
| 9 | >= 450 us |

The final bin is an overflow bin. Every latency value of 450 us or greater is accumulated in bin 9.

One histogram observation is generated for each processed scheduler slot.

For the observed Tb3 example:

```json
"latency_histogram": [999, 1, 0, 0, 0, 0, 0, 0, 0, 0]
```

the interpretation is:

```text
999 scheduler-slot decisions: 0-49 us
  1 scheduler-slot decision : 50-99 us
```

The histogram contains 1000 observations in this particular report.

This is consistent with the observed Tb3 scheduler reporting window. The value 1000 shall not be hard-coded as a universal histogram sample count; the histogram sum represents the number of scheduler-slot observations accumulated in the corresponding reporting window.

### 7.4 Reset semantics

After a cell metrics report is generated, the scheduler resets:

```cpp
error_indication_counter = 0;
decision_latency_sum      = std::chrono::microseconds{0};
decision_latency_hist     = {};
```

Therefore:

- `error_indication_count` is a per-report-window counter;
- `average_latency` describes the current reporting window;
- `latency_histogram` describes the current reporting window;
- these fields are not cumulative across the lifetime of the gNB process.


## 8. UE-level native scheduler metrics

Each element of the native JSON `ue_list` contains a `ue_container` describing scheduler metrics for one UE.

An observed structure is:

```json
{
  "ue_container": {
    "pci": 1,
    "rnti": 17921,
    "cqi": 15,
    "ri": 1.0,
    "dl_mcs": 0,
    "dl_brate": 0.0,
    "dl_nof_ok": 0,
    "dl_nof_nok": 0,
    "dl_bs": 0,
    "pusch_snr_db": 0.0,
    "pucch_snr_db": 62.766006,
    "ta_ns": "0.000000",
    "ul_mcs": 0,
    "ul_brate": 0.0,
    "ul_nof_ok": 0,
    "ul_nof_nok": 0,
    "bsr": 0
  }
}
```

The fields in one UE record do not all have the same temporal semantics.

They fall into three main classes:

1. UE identity or radio context;
2. statistics aggregated over the current scheduler reporting window;
3. last-known state variables that may persist across multiple reporting windows.

### 8.1 UE identity fields

#### `pci`

`pci` identifies the Physical Cell ID associated with the UE scheduler metrics.

The native scheduler structure stores it as:

```cpp
pci_t pci;
```

#### `rnti`

`rnti` contains the UE RNTI represented in the JSON output as a numeric `uint16_t`.

For the investigated UE:

```text
rnti = 17921 decimal = 0x4601 hexadecimal
```

This value was consistent with the RNTI observed in the corresponding gNB runtime logs.

### 8.2 CQI

The scheduler accumulates CQI observations received through CSI reports:

```cpp
u.data.cqi.update(csi.first_tb_wideband_cqi->to_uint());
```

At report time the accumulated statistics are copied to:

```cpp
ret.cqi_stats = data.cqi;
```

The JSON consumer emits:

```cpp
std::roundf(ue.cqi_stats.get_mean())
```

when one or more CQI observations exist.

Therefore JSON `cqi` is:

```text
mean CQI over the current scheduler reporting window,
rounded to an integer
```

It is not the last CQI observation.

Temporal class:

```text
report-window aggregate
```

### 8.3 Rank Indicator

RI observations are accumulated from CSI reports:

```cpp
u.data.ri.update(csi.ri->to_uint());
```

The JSON consumer writes:

```cpp
ue.ri_stats.get_mean()
```

Therefore JSON `ri` is:

```text
mean RI over the current scheduler reporting window
```

Temporal class:

```text
report-window aggregate
```

### 8.4 Downlink MCS

For every scheduled DL codeword, the scheduler accumulates the MCS index.

At report generation:

```cpp
uint8_t mcs =
    data.nof_dl_cws > 0
        ? std::roundf(
              static_cast<float>(data.dl_mcs) /
              data.nof_dl_cws)
        : 0;
```

Therefore JSON `dl_mcs` is the rounded mean DL MCS index over the DL codewords observed in the current scheduler reporting window.

Temporal class:

```text
report-window aggregate
```

### 8.5 Uplink MCS

For scheduled PUSCH transmissions the scheduler accumulates the UL MCS index.

At report generation:

```cpp
mcs =
    data.nof_puschs > 0
        ? std::roundf(
              static_cast<float>(data.ul_mcs) /
              data.nof_puschs)
        : 0;
```

Therefore JSON `ul_mcs` is the rounded mean UL MCS index over PUSCH transmissions in the current scheduler reporting window.

Temporal class:

```text
report-window aggregate
```

### 8.6 Downlink bitrate

Internally the scheduler calculates:

```cpp
ret.dl_brate_kbps =
    static_cast<double>(data.sum_dl_tb_bytes * 8U) /
    metric_report_period.count();
```

where the metric report period is expressed in milliseconds.

The JSON consumer then writes:

```cpp
ue.dl_brate_kbps * 1e3
```

Therefore the native JSON field:

```text
dl_brate
```

is expressed in:

```text
bit/s
```

and represents a bitrate calculated over the scheduler metrics reporting window.

It is not an instantaneous link rate sampled at the JSON emission time.

Temporal class:

```text
report-window aggregate
```

### 8.7 Uplink bitrate

The corresponding UL calculation is:

```cpp
ret.ul_brate_kbps =
    static_cast<double>(data.sum_ul_tb_bytes * 8U) /
    metric_report_period.count();
```

The JSON consumer writes:

```cpp
ue.ul_brate_kbps * 1e3
```

Therefore native JSON:

```text
ul_brate
```

is expressed in:

```text
bit/s
```

and represents a bitrate calculated over the scheduler reporting window.

Temporal class:

```text
report-window aggregate
```

### 8.8 Downlink HARQ counters

The scheduler reports:

```cpp
ret.dl_nof_ok  = data.count_uci_harq_acks;
ret.dl_nof_nok =
    data.count_uci_harqs -
    data.count_uci_harq_acks;
```

Therefore:

```text
dl_nof_ok
```

is the number of DL HARQ ACK results accumulated in the current reporting window.

The field:

```text
dl_nof_nok
```

is the number of HARQ results that are not counted as ACK by this implementation, calculated using the formula above.

These are report-window counters, not process-lifetime cumulative counters.

Temporal class:

```text
report-window counter
```

### 8.9 Uplink CRC counters

The scheduler reports:

```cpp
ret.ul_nof_ok  = data.count_crc_acks;
ret.ul_nof_nok =
    data.count_crc_pdus -
    data.count_crc_acks;
```

Therefore:

- `ul_nof_ok` is the number of successful UL CRC results in the current reporting window;
- `ul_nof_nok` is the number of UL CRC PDUs not counted as successful in that window.

These counters are reset when UE report-window statistics are reset.

Temporal class:

```text
report-window counter
```

### 8.10 PUSCH channel-quality metric

The scheduler calculates:

```cpp
ret.pusch_snr_db =
    data.nof_pusch_snr_reports > 0
        ? data.sum_pusch_snrs /
              data.nof_pusch_snr_reports
        : 0;
```

Therefore JSON `pusch_snr_db` is an arithmetic mean over the PUSCH channel-quality reports accumulated during the current scheduler reporting window.

The JSON field is named:

```text
pusch_snr_db
```

However, the upstream indication supplying this value is named:

```text
ul_sinr_dB
```

and the source code describes it as a PUSCH SINR value in dB.

The Sci_O-RAN dataset shall preserve the native JSON field name while documenting this implementation-level naming distinction.

Unit:

```text
dB
```

Temporal class:

```text
report-window aggregate
```

### 8.11 PUCCH channel-quality metric

The scheduler calculates:

```cpp
ret.pucch_snr_db =
    data.nof_pucch_snr_reports > 0
        ? data.sum_pucch_snrs /
              data.nof_pucch_snr_reports
        : 0;
```

Therefore JSON `pucch_snr_db` is an arithmetic mean over the corresponding PUCCH channel-quality reports accumulated during the reporting window.

As with the PUSCH metric, the native JSON field uses an `snr` name while the associated indication path uses an `ul_sinr_dB` value.

Unit:

```text
dB
```

Temporal class:

```text
report-window aggregate
```

### 8.12 Downlink buffer state

The scheduler stores the most recent DL buffer state separately for each logical channel:

```cpp
u.last_dl_bs[dl_bs.lcid] = dl_bs.bs;
```

At report generation:

```cpp
ret.dl_bs = 0;

for (const unsigned value : last_dl_bs) {
  ret.dl_bs += value;
}
```

The source value originates from the RLC TX entity buffer-state interface.

The RLC API defines the buffer state as the gross total size required to fully flush the RLC TX entity.

For example, the TM implementation returns:

```cpp
sdu_queue.get_state().n_bytes + sdu.buf.length()
```

Therefore JSON `dl_bs` represents:

```text
sum of the last-known RLC TX buffer-state values
across the UE logical channels
```

Unit:

```text
bytes
```

Temporal class:

```text
last-known state
```

`dl_bs` is not averaged over the scheduler reporting interval.

### 8.13 Uplink Buffer Status Report

For each received UL BSR the scheduler clears the previously stored value and sums the reported Logical Channel Group values:

```cpp
u.last_bsr = 0;

for (unsigned i = 0;
     i != bsr.reported_lcgs.size();
     ++i) {
  u.last_bsr +=
      bsr.reported_lcgs[i].nof_bytes;
}
```

Each LCG report contains:

```cpp
uint32_t nof_bytes;
```

Therefore JSON `bsr` represents:

```text
last-known total UL buffer occupancy
summed across the LCGs contained in the most recent BSR
```

Unit:

```text
bytes
```

Temporal class:

```text
last-known state
```

It is not an average over the reporting window.

### 8.14 Timing advance

The scheduler receives:

```cpp
std::optional<phy_time_unit> time_advance_offset;
```

described in the source as:

```text
Timing Advance Offset measured for the UE
```

The most recently available value is retained as `last_ta`.

The JSON serializer converts the value using:

```cpp
ue.last_ta->to_seconds<float>() * 1e9
```

and serializes the result as a string.

Therefore JSON `ta_ns` is:

```text
last-known measured UE timing-advance/time-alignment offset
converted to nanoseconds
```

Unit:

```text
ns
```

Native JSON type:

```text
string
```

If no timing-advance value is available, the serializer uses:

```text
n/a
```

Temporal class:

```text
last-known state
```

`ta_ns` must not be interpreted as IP latency, RTT, or end-to-end user-plane delay.

### 8.15 Reset and persistence semantics

At the end of every UE metrics report, the scheduler invokes:

```cpp
reset();
```

which resets the current-window statistics:

```cpp
data = {};
```

Consequently, report-window statistics such as bitrate, MCS, HARQ/CRC counters, and channel-quality aggregates are recomputed independently for each reporting window.

The persistent state variables are stored separately from `data`.

In particular:

```text
last_bsr
last_dl_bs
last_ta
```

are not reset by the report-window statistics reset.

Therefore these values may legitimately repeat across consecutive JSON records when no newer corresponding indication has been received.

### 8.16 Temporal classification summary

| Native JSON field | Unit | Temporal semantics |
|---|---|---|
| `pci` | identifier | UE/cell context |
| `rnti` | identifier | UE context |
| `cqi` | index | mean over report window, rounded |
| `ri` | rank | mean over report window |
| `dl_mcs` | MCS index | mean over report window, rounded |
| `dl_brate` | bit/s | report-window bitrate |
| `dl_nof_ok` | count | report-window HARQ ACK counter |
| `dl_nof_nok` | count | report-window non-ACK HARQ counter |
| `dl_bs` | bytes | last-known state, summed over LCIDs |
| `pusch_snr_db` | dB | report-window mean of native PUSCH channel-quality reports |
| `pucch_snr_db` | dB | report-window mean of native PUCCH channel-quality reports |
| `ta_ns` | ns | last-known timing offset; JSON string |
| `ul_mcs` | MCS index | mean over report window, rounded |
| `ul_brate` | bit/s | report-window bitrate |
| `ul_nof_ok` | count | report-window successful CRC counter |
| `ul_nof_nok` | count | report-window unsuccessful CRC counter |
| `bsr` | bytes | last-known UL BSR state |


## 9. Formal native telemetry schema

### 9.1 Schema design principle

The native gNB JSON message is hierarchical:

```text
root telemetry record
  |
  +-- timestamp
  |
  +-- cell_metrics
  |
  +-- ue_list[]
  |     |
  |     +-- ue_container
  |
  +-- event_list[]
```

A single UDP datagram can therefore contain:

- one root timestamp;
- one set of cell-level metrics;
- zero or more UE metric containers;
- zero or more scheduler events.

For the future unified Sci_O-RAN dataset, the native telemetry should not be flattened by discarding this hierarchy.

The recommended normalized representation consists of three logically related tables:

```text
native_gnb_record
native_gnb_ue
native_gnb_event
```

All child records shall reference a unique native telemetry `record_id`.

### 9.4 Native `ta_ns` type handling

The native serializer declares:

```text
ta_ns
```

as a string.

Examples include:

```text
"0.000000"
```

and, when no value exists:

```text
"n/a"
```

The raw representation shall therefore be retained as:

```text
ta_ns_raw
```

A processed numeric field may additionally be created:

```text
ta_ns
```

with the conversion rule:

```text
numeric string -> float64 nanoseconds
"n/a"          -> null
```

The raw field must not be overwritten by the processed numeric representation.

### 9.5 Missing-value handling

Native scheduler metrics do not all have observations in every reporting interval.

The unified dataset shall distinguish:

```text
0
```

from:

```text
no observation / unavailable
```

where the source semantics permit this distinction.

A zero physical or scheduler value must not automatically be converted to `null`.

Similarly, missing or unavailable values must not be silently replaced with zero during dataset normalization.

The raw JSON record remains the authoritative source for resolving ambiguities in processed representations.

### 9.6 `native_gnb_event`

The native JSON root can also contain:

```text
event_list[]
```

Each event contains scheduler-event context including:

```text
sfn
slot_index
rnti
event_type
```

The recommended event schema is:

| Field | Native source | Type | Unit | Meaning |
|---|---|---|---|---|
| `record_id` | parent record | string | - | link to native telemetry record |
| `event_index` | dataset-generated | uint16 | - | event position within the record |
| `sfn` | event `sfn` | uint16 | radio frame index | System Frame Number |
| `slot_index` | event `slot_index` | uint16 | slot index | scheduler slot index |
| `rnti` | event `rnti` | uint16 | identifier | affected UE RNTI |
| `event_type` | event `event_type` | string | - | scheduler event type |

The exact source implementation defines event types corresponding to:

```text
ue_create
ue_reconf
ue_rem
```

The raw event string shall be preserved without reinterpretation.

### 9.7 Recommended derived timing fields

Processed datasets may calculate the following derived values:

| Derived field | Definition | Unit |
|---|---|---:|
| `gnb_dt_ms` | difference between consecutive `gnb_timestamp_s` values | ms |
| `rx_mono_dt_ms` | difference between consecutive `rx_mono_ns` values | ms |
| `rx_wall_minus_gnb_ms` | `rx_wall_ns / 1e6 - gnb_timestamp_s * 1e3` | ms |
| `latency_hist_count` | sum of histogram bins 0 through 9 | count |

These are derived quantities and must never replace their source fields.

Their provenance shall identify the exact transformation used to calculate them.

### 9.8 Record ordering

For native telemetry processing, the preferred ordering rule is:

```text
primary ordering   = rx_mono_ns
source-time field  = gnb_timestamp_s
```

`rx_mono_ns` provides a robust local ordering for records received by the host.

`gnb_timestamp_s` remains the authoritative native gNB wall-clock timestamp and is required for cross-source epoch-based alignment.

Both shall be retained.

### 9.9 Schema evidence classes

Every metric definition in the future machine-readable dataset schema should carry an evidence class.

The following values are recommended:

| Evidence class | Meaning |
|---|---|
| `SOURCE_PROVEN` | semantics or unit established directly from the exact runtime source revision |
| `RUNTIME_OBSERVED` | property directly demonstrated in the Tb3 runtime |
| `DERIVED` | calculated deterministically from source or receiver fields |
| `HYPOTHESIS` | interpretation not yet proven and not permitted as an established dataset fact |

For the fields documented in Sections 5-9, metric units and temporal aggregation semantics are classified as `SOURCE_PROVEN` unless explicitly stated otherwise.

The transport addresses, observed source port, and measured interval statistics are `RUNTIME_OBSERVED`.

Derived timing deltas are `DERIVED`.

Hypotheses shall never be silently promoted to `SOURCE_PROVEN`.


## 10. Evidence status and interpretation boundaries

The Sci_O-RAN documentation workflow distinguishes facts established from the exact implementation, facts observed experimentally at runtime, deterministic derived quantities, and hypotheses that still require experimental verification.

Native gNB telemetry shall be interpreted according to these evidence classes.

### 10.1 Source-proven facts

The following properties are established directly from the exact srsRAN source revision used by the running Tb3 gNB:

```text
9d5dd742a70e82c0813c34f57982f9507f1b6d5d
```

The following statements are therefore classified as `SOURCE_PROVEN`:

- `sched_report_period` is interpreted as a scheduler metrics period in milliseconds;
- scheduler reports are generated according to scheduler-slot progression;
- the native JSON timestamp is generated from `std::chrono::system_clock`;
- the native JSON timestamp is represented in UNIX seconds with millisecond implementation resolution;
- `average_latency` is the mean internal scheduler decision latency;
- the unit of `average_latency` is microseconds;
- the latency histogram contains ten 50-us bins, with the final bin acting as an overflow bin;
- `cqi` is a report-window CQI mean rounded to an integer when observations are available;
- `ri` is a report-window mean;
- `dl_mcs` and `ul_mcs` are rounded report-window means;
- `dl_brate` and `ul_brate` are report-window bitrate values exported in bit/s;
- `dl_nof_ok` and `dl_nof_nok` describe DL HARQ results for the current report window;
- `ul_nof_ok` and `ul_nof_nok` describe UL CRC results for the current report window;
- `dl_bs` is derived from last-known RLC TX buffer-state information;
- `bsr` is derived from the most recent UL BSR and represents bytes summed across the reported LCGs;
- `ta_ns` contains the last-known timing-advance/time-alignment offset converted to nanoseconds;
- `ta_ns` is serialized as a string and can contain `n/a`;
- `last_dl_bs`, `last_bsr`, and `last_ta` persist independently of the report-window statistics reset;
- native scheduler event strings are `ue_create`, `ue_reconf`, and `ue_rem`;
- the native JSON metrics path uses the configured UDP sink;
- native JSON scheduler telemetry and E2SM-KPM telemetry are distinct telemetry paths.

These properties may be used as established semantic definitions for the current runtime revision.

## 11. Known limitations

### 11.1 UDP delivery has no telemetry sequence number

The native transport uses UDP.

The observed JSON schema does not provide a dedicated monotonically increasing telemetry-record sequence number.

Consequently, a gap between two received timestamps cannot by itself prove whether:

- a UDP datagram was lost;
- a scheduler report was delayed;
- a report was not generated at the nominal wall-clock time;
- runtime execution temporarily progressed more slowly.

Future capture pipelines shall therefore preserve both source and receive timestamps and shall avoid automatically classifying every enlarged interval as packet loss.

### 11.2 Zero-value ambiguity for metrics without observations

Some report-window metrics use zero when no source observations are available during the current reporting interval.

For example, the scheduler calculation for the PUSCH channel-quality metric contains:

```cpp
data.nof_pusch_snr_reports > 0
    ? data.sum_pusch_snrs / data.nof_pusch_snr_reports
    : 0;
```

A runtime JSON example contained:

```json
"pusch_snr_db": 0.0
```

Consequently, for fields with this implementation behaviour, a numeric zero can be semantically ambiguous: it can represent the default produced when no observations were accumulated, while zero can also be a physically meaningful numeric value in some measurement domains.

Therefore the normalization pipeline shall not invent certainty that is absent from the native schema.

In particular:

```text
raw value = 0
```

must not automatically be relabelled as either:

```text
valid measured zero
```

or:

```text
missing value
```

unless additional source information establishes the interpretation.

The raw JSON value shall always be retained.

A future enhancement of the telemetry pipeline may add explicit observation counters or validity indicators where required for statistical analysis.

### 11.3 Native JSON `ta_ns` is not numerically typed

Although `ta_ns` represents nanoseconds, the native JSON serializer exports it as a string.

The dataset normalization layer must therefore perform explicit parsing and retain the original raw value.

The token:

```text
n/a
```

shall be mapped to a missing numeric value only in the processed representation.

### 11.4 Native scheduler latency is not user-plane latency

The field:

```text
cell_metrics.average_latency
```

and its compact-parser alias:

```text
cell_avg_latency
```

describe internal scheduler decision latency only.

Neither field can be used as a substitute for:

```text
ping RTT
iperf application/user-plane timing
UE-to-UPF latency
end-to-end packet latency
```

Those quantities require independent measurements and shall later be aligned with native telemetry through the unified Sci_O-RAN time model.

### 11.5 UDP source port is not stable schema metadata

The observed source port:

```text
52084
```

belongs to the investigated runtime instance.

It shall be recorded as per-datagram transport metadata but shall never be used as a fixed identifier of the native telemetry service.

The stable configured endpoint is the destination:

```text
10.53.1.1:55555/udp
```

for the investigated BASE-05 configuration.

## 12. Open hypotheses

### 12.1 Effective reporting interval

The configured scheduler reporting period is:

```text
1000 ms
```

while the measured effective Tb3 wall-clock interval was approximately:

```text
1065.7 ms
```

The cause of this difference has not yet been proven.

One possible hypothesis is that the scheduler-slot progression of the ZeroMQ-based Tb3 radio runtime does not advance at exactly real-time wall-clock speed under the investigated execution conditions.

Other runtime scheduling or processing effects may also contribute.

This explanation remains a:

```text
HYPOTHESIS
```

and must not be represented as an established property of srsRAN, ZeroMQ, or Tb3 until a dedicated experiment demonstrates the cause.

A future timing experiment should compare:

- scheduler slot progression;
- gNB system-clock progression;
- host monotonic time;
- CPU utilization;
- container scheduling;
- ZeroMQ radio execution timing.

### 12.2 Telemetry delivery completeness

The current native JSON stream does not provide sufficient information to distinguish every delayed report from a lost UDP report.

Therefore telemetry-delivery completeness is not yet formally proven.

A future reproducibility experiment may introduce receiver-side continuity checks and, if necessary, an additional sequence identifier in the Sci_O-RAN collection layer.

## 14. Native telemetry rules for subsequent Sci_O-RAN work

The following rules are normative for subsequent experiments:

1. Preserve the original gNB JSON timestamp.
2. Preserve host receive wall-clock and monotonic timestamps.
3. Do not assume a strict native telemetry sampling period of 1 s.
4. Calculate inter-arrival intervals from actual timestamps.
5. Prefer the host monotonic clock for local receive-interval calculations.
6. Preserve the raw JSON representation before normalization.
7. Preserve metric units explicitly in processed field names.
8. Distinguish report-window aggregates from last-known state variables.
9. Do not interpret `average_latency` or `cell_avg_latency` as RTT.
10. Do not interpret `ta_ns` as network latency.
11. Preserve native PUSCH/PUCCH field names while documenting the upstream SINR naming.
12. Do not treat the observed UDP source port as a fixed service port.
13. Keep native JSON telemetry logically separate from E2SM-KPM telemetry.
14. Keep source-proven facts, runtime observations, derived values, and hypotheses explicitly separated.
15. Associate future telemetry datasets with exact gNB source revision and Docker image provenance.

## 15. Conclusion

The Sci_O-RAN Tb3 native gNB telemetry path has been traced from the srsRAN scheduler through the JSON metrics consumer and UDP sink to the host-side receiver.

The meaning, units, temporal behaviour, and persistence characteristics of the principal native cell and UE metrics have been established from the exact runtime source revision and validated against real Tb3 JSON telemetry.

The investigation also demonstrates that the configured 1000 ms scheduler report period must not be treated as an exact 1 s wall-clock sampling interval. Actual source and receive timestamps are therefore mandatory for future time-series alignment.

The schema defined in this document provides the native-gNB component of the future unified Sci_O-RAN experimental dataset while preserving the distinction between source facts, runtime observations, derived quantities, and unresolved hypotheses.
